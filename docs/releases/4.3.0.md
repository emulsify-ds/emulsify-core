# Emulsify Core 4.3.0

Emulsify Core 4.3.0 is a minor release focused on making current Core behavior
safer to consume and easier to verify. It adds a focused Storybook adapter for
autonomous custom elements, versions the `emulsify-audit` JSON contract,
improves Twig compilation and hot-module replacement (HMR), and tests the
dependency contract against clean installations of the packed package.

The release also makes an important compatibility requirement explicit:
consumers need Node.js 24.13.0 or later. Repository development and CI use the
exact Node.js 24.13.0 version pinned in `.nvmrc`.

## Custom Element Storybook API

This release adds two named exports to the established
`@emulsify/core/storybook` entry point:

- `defineCustomElement(tagName, ElementClass, options?)` registers an
  autonomous custom element safely during repeated story evaluation.
- `renderWebComponent(tagName, options?)` creates a React-compatible Storybook
  render function that applies Storybook args to the custom-element host.

```js
import {
  defineCustomElement,
  renderWebComponent,
} from '@emulsify/core/storybook';
import { fn } from 'storybook/test';
import { GreetingCardElement } from './greeting-card.js';

defineCustomElement('greeting-card', GreetingCardElement);

export default {
  title: 'Components/Greeting Card',
  render: renderWebComponent('greeting-card', {
    // Property mode is the default.
    argsAs: 'properties',
    events: {
      'greeting-select': 'onGreetingSelect',
    },
  }),
  args: {
    heading: 'Hello',
    items: [{ label: 'Alpha' }, { label: 'Beta' }],
    children: 'Content for the default slot',
    onGreetingSelect: fn(),
  },
};

export const Default = {};
```

`defineCustomElement()` validates the browser custom-element name rules and
requires a constructable class whose prototype inherits from `HTMLElement`.
Customized built-in elements, including constructors derived from interfaces
such as `HTMLButtonElement` and registration options such as
`{ extends: 'button' }`, are rejected.

The helper returns the registered constructor. Repeating the same tag and
constructor is safe, which supports story remounts and repeated module
evaluation. If HMR evaluates the tag with a different constructor, the browser
registry cannot replace the existing definition; Core warns, returns the
browser-registered constructor, and asks the developer to refresh Storybook.

### Argument, Slot, Event, And Shadow-DOM Behavior

| Area               | Supported behavior                                                                                                                                                                                                                                                                       |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Properties         | This is the default `argsAs` mode. Args are assigned directly to DOM properties, so objects, arrays, functions, booleans, `null`, and `undefined` retain their JavaScript types. When a later args object omits a previously applied key, Core assigns `undefined` to clear stale state. |
| Attributes         | Set `argsAs: 'attributes'` to use attributes. Values are stringified, `true` creates an empty attribute, and `false`, `null`, or `undefined` removes it. Omitting a previously applied key also removes its attribute.                                                                   |
| Default slot       | `args.children` becomes React-managed light DOM inside the custom element. Strings are text, React-renderable nodes are accepted, and omitting `children` removes old content. An element with an unnamed `<slot>` receives this content.                                                |
| Native events      | The `events` option maps a native event type to a Storybook callback arg. The callback receives the original `Event` or `CustomEvent`, including `event.detail`. Listeners update with args and are removed during cleanup. Callback args are not forwarded to the element.              |
| Shadow DOM         | The component owns its shadow root; Core applies args and listeners to the host. The built browser fixture proves property and attribute updates, default-slot assignment, a host-dispatched `CustomEvent`, and an axe scan that reaches a button in an open shadow root.                |
| Wrapper, class, ID | Without `wrapper`, the renderer's `className` and `id` options apply to the custom element. With a wrapper tag or component, those options apply to the wrapper while Storybook args still target the custom element. Internal renderer options are not forwarded.                       |

Only `properties` and `attributes` are valid `argsAs` values. Unsupported
values fail with an error that identifies the option and accepted values.
Event maps likewise require non-empty native event names and non-empty callback
arg names; a present callback arg must be a function, `null`, or `undefined`.

Controls update the existing custom-element instance rather than forcing a
page reload. The renderer remembers which properties or attributes it applied,
clears omitted values on the next render, and removes native listeners on
unmount.

### Known Custom Element Limitations

- The adapter supports autonomous custom elements only. It does not support
  customized built-in markup such as `<button is="custom-button">`.
- `args.children` provides an unnamed default-slot path. There is no dedicated
  named-slot composition API in this release.
- Native events require an explicit `events` map. React-style `on*` arg names
  are not inferred as native listeners.
- An event dispatched from within a shadow tree needs `composed: true` to cross
  the shadow boundary. Use `bubbles: true` when it must continue through
  ancestor elements, or redispatch the public event from the host.
- Core does not create, replace, or inspect a component's shadow root. The
  browser test covers one open shadow-root fixture; it is not evidence that
  Storybook's a11y addon automatically traverses every open or closed shadow
  root.
- The browser custom-element registry is permanent for a page. A constructor
  change during HMR requires a full Storybook refresh after Core reports the
  mismatch.

## Audit JSON Contract

`emulsify-audit --json` is a versioned machine-readable interface in 4.3.0.
The schema version is independent of the Core package version. Schema version 1
uses one JSON document on stdout for both completed scans and CLI/setup
failures.

```json
{
  "schemaVersion": 1,
  "tool": {
    "name": "@emulsify/core",
    "version": "4.3.0"
  },
  "root": ".",
  "summary": {
    "error": 0,
    "warn": 1,
    "info": 0
  },
  "files": {
    "stories": 1,
    "twig": 1,
    "code": 1,
    "styles": 0
  },
  "findings": [
    {
      "id": "legacy-twig-story",
      "severity": "warn",
      "path": "src/components/card/card.stories.js",
      "line": 5,
      "message": "Twig story appears to return an HTML string directly. This remains compatible, but renderTwig() is preferred for active migrations.",
      "details": [
        "imports Twig templates without renderTwig()",
        "appears to return Twig HTML strings directly"
      ],
      "docs": "https://github.com/emulsify-ds/emulsify-core/blob/4.x/docs/storybook.md#legacy-twig-story-compatibility"
    }
  ]
}
```

The contract guarantees the required top-level fields and value types, severity
names, finding field names and types, and existing finding IDs. An incompatible
change to those fields or meanings requires a `schemaVersion` increase. New
finding IDs and optional fields are compatible additions. Messages, details,
documentation URLs, counts, and ordering may change as checks improve. Ordering
is deterministic for reproducible output, but consumers should select fields
and findings by name or ID instead of treating order as semantic.

`root` is always `"."`. Finding paths are project-relative POSIX-style paths
without a leading `./`. Optional `path`, `line`, `details`, and `docs` fields
are omitted when unavailable instead of appearing as `null` or `undefined`.
The formatter removes the selected project root from finding messages and
details. Other configured values in that human-readable text are not structured
paths and should not be parsed as such. The `files` categories can overlap; they
are scan-set counts, not a unique-file total.

Failure thresholds have these exit semantics:

| Option            | Completed findings that produce exit status 1 |
| ----------------- | --------------------------------------------- |
| No threshold      | None; findings do not fail by default         |
| `--fail-on error` | Errors                                        |
| `--fail-on warn`  | Errors or warnings                            |
| `--fail-on info`  | Errors, warnings, or informational findings   |
| `--fail-on any`   | Any finding                                   |
| `--fail-on-found` | Compatibility alias for `--fail-on any`       |

Exit status 0 means the scan completed below its threshold. Exit status 1
means it completed and met the threshold; it still emits a normal report. Exit
status 2 means argument parsing, setup, or execution failed. JSON failures use
the same `schemaVersion` and `tool` identity with a distinct error envelope:

```json
{
  "schemaVersion": 1,
  "tool": {
    "name": "@emulsify/core",
    "version": "4.3.0"
  },
  "error": {
    "code": "invalid-arguments",
    "message": "--fail-on must be one of: error, warn, info, any."
  }
}
```

The error code is `invalid-arguments` for command-line failures and
`audit-failed` for setup or scan failures. JSON mode does not mix usage text or
human prose into stdout.

The focused `emulsify-audit-twig-stories --json` command uses the same envelope
and normalized finding shape. Its existing `--fail-on-found` flag remains the
failure switch for that focused migration scan.

Preserve the audit status while inspecting the report in CI:

```sh
status=0
npx --no-install emulsify-audit --json --fail-on warn > audit-report.json || status=$?
jq '{summary, files}' audit-report.json
exit "$status"
```

Or let `jq` enforce a custom policy while the audit remains non-failing:

```sh
npx --no-install emulsify-audit --json |
  jq -e '.summary.error == 0 and .summary.warn == 0'
```

See [Project Audit](../audit.md) for the complete field-level stability policy
and more examples.

## Twig And Vite Runtime Changes

### Template Dependencies, Cache, And HMR

Twig template compilation now uses asynchronous file metadata and reads, and
independent sibling dependencies can compile in parallel. Compile results and
include-resolution probes use bounded least-recently-used caches instead of
unbounded process-lifetime maps.

When multiple emitted Twig modules share a static dependency, generated
private virtual modules carry the compiled dependency parameters so Vite can
share that emitted dependency data instead of repeating the same compiled
abstract syntax tree in every importer. These virtual module IDs are internal
implementation details.

HMR maintains a reverse graph from included Twig files to their importing
modules. Changing a known template clears its compile entry and relevant
resolution entries, invalidates the shared dependency module, and invalidates
all known importers. Creating or deleting a Twig file clears the broader
resolution cache because a prior resolution miss may have changed. Vituum's
full-page Twig reload is disabled so Core's module invalidation can update the
story without reloading the entire iframe.

Template IDs, Storybook glob keys, and asset-root keys now use one
project-root-relative path normalization algorithm, including Windows
backslash and repeated-slash cases. This prevents a compiled template ID and
its generated glob key from diverging.

### `source()`, Asset Roots, And Lazy Loading

Compiled Twig modules remain eager because Storybook render functions are
synchronous. Raw Twig source and text asset strings remain lazy and are cached
only after `source()` requests them. The first render can complete without a
new lazy source while its import resolves; Core then re-renders the Twig story,
and later reads are synchronous from memory.

For `source('@assets/...')`, Core generates lazy text imports from configured
`assets.roots` plus existing project `assets` and `src/assets` directories.
Inline text support covers SVG, HTML, Twig, CSS, JavaScript, JSON, TXT, and
Markdown. Generated aliases such as `@assets/icons.svg` prefer generated
`dist/assets` output before project-authored roots. Raster images continue to
produce image markup, while fonts and other binary assets use public
`/assets/...` URLs.

The synchronous XHR code path is disabled by default because it blocks the
browser main thread. Its deprecated
`platformAdapter.storybook.allowSyncXhrSource` opt-in is reached only when the
generated module reports no asset-root coverage; it is not a general fallback
for a file missing from an otherwise active generated asset map.

The asset lookup and cache implementation is shared by Core's generated
virtual module, but it is not a consumer JavaScript API. The implementation
file is included in the tarball because the installed Vite plugin loads it
through a private virtual module. The package explicitly does not export:

```text
@emulsify/core/storybook/twig/asset-source-runtime
```

Consumers configure `assets.roots` and use Twig's `source()` function instead.
The packed Storybook smoke test proves that this private runtime loads from an
installed tarball.

## Executable Consumer Dependency Contract

`config/consumer-contract.json` now connects dependency metadata to executable
packed-consumer fixtures. The runner creates one Core tarball, installs it into
clean temporary npm projects without source-checkout symlinks, checks that
contract dependencies resolve from the consumer's flat `node_modules`, runs
finite representative scripts, checks output and Storybook IDs, and removes
the temporary projects and tarball.

| Fixture           | Consumer shape                                       | Executed behavior                                                                    |
| ----------------- | ---------------------------------------------------- | ------------------------------------------------------------------------------------ |
| `whisk-drupal`    | Drupal Whisk-like generated theme                    | ESLint, Stylelint, Jest/jsdom, Vite and Storybook builds, and Pa11y/axe in a browser |
| `none`            | Generated `none` platform theme                      | Vite build, output assertions, and a `normalize.css` consumer import                 |
| `wordpress-twig`  | WordPress/Twig generated theme                       | Vite build and WordPress/Twig output assertions                                      |
| `mixed-storybook` | Twig, React, and autonomous custom-element Storybook | Storybook build and expected story IDs with React/React DOM 18.3.1 and 19.2.7        |

The manifest keeps long-running generated scripts such as `develop`, `vite`,
`storybook`, `coverage`, and `twatch` for metadata coverage, but the fixture
runner executes only finite scripts.

This contract intentionally covers npm's default flat `node_modules` layout for
the generated-theme pattern where `@emulsify/core` is the primary tooling
dependency. pnpm's isolated linker and Yarn Plug'n'Play are not supported for
that one-dependency pattern unless the consuming project directly declares
every tool it invokes.

See [Dependency Contract](../dependency-contract.md) for the package-to-script
mapping and fixture update procedure.

## Dependency Compatibility Changes

The direct dependency changes with consumer or maintainer impact are:

| Change                                        | Compatibility impact                                                                                                                                                                                                                                           |
| --------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Babel remains on 7.29.x                       | `@babel/core`, `@babel/eslint-parser`, and `@babel/preset-env` remain on the latest 7.x line. Jest's current syntax-plugin chain does not yet declare Babel 8 peers, so holding the supported line avoids an invalid npm dependency tree and install warnings. |
| `concurrently` 9 to 10                        | Generated `develop` scripts continue to use the hoisted binary and are covered by the dependency contract. Projects that use undocumented `concurrently` APIs should declare and test their own direct dependency.                                             |
| `js-yaml` 4 to 5                              | Core's maintained YAML loader now uses the 5.x parser. Consumer code should not rely on Core to provide `js-yaml` transitively; declare it directly when importing it.                                                                                         |
| Restored Emulsify CLI compatibility bridge    | `@emulsify/cli` remains a direct Core dependency at `^2.2.0`, preserving the project-local `emulsify` binary supplied by Core 4.2. Global or direct CLI installation remains the supported path for `emulsify init` before a project exists.                   |
| Removed direct tooling dependencies           | `vite-plugin-static-copy`, `vite-plugin-svg-sprite`, and `yaml` were removed from Core's direct dependencies after Core and known generated-consumer use was checked. Projects that import or invoke them must add their own dependency.                       |
| Added `puppeteer` as a development dependency | Puppeteer drives the built Storybook browser fixture. It is release-test tooling, not part of Core's generated-consumer dependency contract.                                                                                                                   |

Installing Core supplies the project-local `emulsify` binary through the
published CLI package as a Core 4.x compatibility bridge. The packed smoke test
proves that a clean project installing only Core can run
`npx --no-install emulsify --help` from that dependency. This binary remains
separate from Core's `emulsify-audit` and `emulsify-audit-twig-stories`
executables.

## Node.js Support Policy

Emulsify Core 4.3.0 declares:

```json
{
  "engines": {
    "node": ">=24.13.0"
  }
}
```

This exact patch floor is a consumer requirement, not only a preferred
repository version. `stylelint-selector-bem-pattern` 5 declares Node.js
`>=24.13.0` and determines Core's floor. The Stylelint plugin was already a 5.x
dependency in 4.2.0; 4.3.0 corrects the public engine contract to reflect its
installed requirement rather than presenting that package as a new upgrade.

Repository contributors and all CI/release workflows use exactly Node.js
24.13.0 through `.nvmrc`. Maintained npm scripts run the Node version check,
which reads `package.json#engines.node`; the minimum is not repeated in the
script implementation.

This policy applies to 4.3.0. Published 3.x releases and Core 4.0 through 4.2
declared the broader `>=24` contract and did not claim a patch-specific floor.

## Public Package Exports

The `package.json#exports` subpath map is unchanged from 4.2.0: 4.3.0 does not
add, remove, or retarget a public package path.

The release adds these named exports to the existing
`@emulsify/core/storybook` barrel:

```js
import {
  defineCustomElement,
  renderWebComponent,
} from '@emulsify/core/storybook';
```

There is no separate custom-element subpath. There is also no public Twig
asset-source-runtime subpath. Internal Vite plugin files were reorganized
inside the tarball, but consumers should continue to use the established
public paths:

- `@emulsify/core`
- `@emulsify/core/extensions`
- `@emulsify/core/extensions/react`
- `@emulsify/core/extensions/twig`
- `@emulsify/core/storybook`
- `@emulsify/core/storybook/twig/drupal-filters`
- `@emulsify/core/storybook/twig/include-function`
- `@emulsify/core/storybook/twig/source-function`
- `@emulsify/core/storybook/twig/source`
- `@emulsify/core/vite`
- `@emulsify/core/vite/plugins`
- `@emulsify/core/vite/platforms`
- `@emulsify/core/package.json`

`emulsify-audit` and `emulsify-audit-twig-stories` remain package executables,
not JavaScript export subpaths.

## Migration Actions For Existing Projects

1. Update development, CI, and production build environments to Node.js
   24.13.0 or later before installing Core 4.3.0.
2. Reinstall from the lockfile. Custom Babel and ESLint integrations remain on
   the supported Babel 7.29.x line for this release.
3. Import the custom-element helpers from `@emulsify/core/storybook`. Do not
   add a deep import for the internal Twig asset-source runtime or private Vite
   plugin files.
4. If Twig `source('@assets/...')` reads text outside `assets`, `src/assets`, or
   configured `assets.roots`, move the file into a supported root. Do not rely
   on the deprecated synchronous XHR opt-in as a general missing-file fallback.
5. If CI consumes `emulsify-audit --json`, select fields by name, record
   `schemaVersion`, distinguish exit status 1 findings from exit status 2 CLI
   failures, and update any old `--fail-on-found` use when a narrower
   `--fail-on` threshold is appropriate.
6. Install `@emulsify/cli` globally or directly when scaffolding with
   `emulsify init`. Installed Core 4.x projects continue to receive the local
   CLI compatibility binary. Declare `vite-plugin-static-copy`,
   `vite-plugin-svg-sprite`, `yaml`, or any other invoked tool directly rather
   than relying on Core's former transitive installation.
7. Generated themes that rely on Core's hoisted toolchain should use npm's flat
   install model or declare each tool directly under another package manager.
8. Run the project audit and release-relevant project scripts:

   ```sh
   npx --no-install emulsify-audit
   npm run build
   npm run storybook-build
   ```

Projects migrating from pre-4.x Webpack releases should also follow
[Migration To Core 4](../migration-4x.md).

## Release Verification And CI Evidence

From a clean checkout, install the locked dependencies and run the aggregate
verification command:

```sh
npm ci
npm run release:verify
```

`release:verify` runs linting, unit tests, the repository Storybook build, every
release fixture, every packed consumer fixture and React peer version, the
package dry run, the packed-package smoke test, and non-publishing release
analysis.

The read-only pull-request CI workflow separates that evidence into parallel
jobs:

| CI job                | Evidence                                                                                                                                                                                                             |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `release-readiness`   | Markdown/Prettier and JavaScript linting, the complete Jest suite—including package-export and internal-path assertions—and the repository Storybook production build                                                |
| `fixture-builds`      | Drupal SDC, `none`, WordPress, legacy, structure-implementation, mixed Storybook, and large-Twig fixtures                                                                                                            |
| `package-readiness`   | Package-content dry run, a clean tarball install, native ESM public imports, rejection of the internal asset-runtime subpath, installed audit JSON, packed Storybook build, and safe release analysis for `main` PRs |
| `consumer-fixtures`   | Clean packed-package installs and representative Drupal Whisk, `none`, and WordPress/Twig scripts                                                                                                                    |
| `react-peer-fixtures` | Packed mixed Storybook builds with React and React DOM 18.3.1 and 19.2.7                                                                                                                                             |

The mixed Storybook release fixture builds Twig, React, property-mode custom
element, and attribute-mode custom element stories together. Its Chromium test
changes a Storybook control without a page reload, preserves object/array
properties, clears an omitted property, adds and removes a boolean attribute,
checks default-slot content, receives the original native `CustomEvent`, and
runs axe against an open shadow root. On failure, CI uploads the manager HTML,
screenshot, browser messages, and captured custom-element state.

The package smoke test installs the tarball without repository symlinks, imports
all intentional public API groups, confirms the Twig asset runtime cannot be
deep-imported, executes the installed audit CLI in JSON mode, and builds a
mixed Twig, React, and custom-element Storybook from the installed package.
Package-export tests also verify that every export target and packaged relative
runtime import exists while tests, snapshots, coverage output, and release-only
scripts remain excluded.

For focused local checks:

```sh
npm run lint
npm test
npm run storybook-build
npm run fixtures:release -- --fixture mixed-storybook
npm run fixtures:consumer
npm run pack:dry-run
npm run smoke:pack
npm run release:analyze
```

Pull-request CI has only `contents: read` permission and cannot publish. The
publish workflow runs only on `main`; it performs
`npm run semantic-release -- --dry-run` before the separate publishing step.
The dry run calculates the release without publishing a package, tag, or GitHub
release. See [Release Verification](../release.md) for merge-strategy and
semantic-release guidance.
