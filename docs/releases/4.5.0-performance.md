# 4.5.0 developer workload measurements

Measured September 9, 2026 for PR #314. These local measurements cover source
implementation effects in audits, grouped template lookup, and accessibility
scanning. They do not measure Storybook startup, interaction, or production
build performance.

## Revisions and controls

- Release base: `a0c08cf1e409138ffd008a882394e5c2001e5bef` (`v4.4.0`,
  the verified PR base on `origin/main`). The local `main` reference was older.
- Release before optimization: `e9e701cc1824ffe37a835b4b5ff8dab52319b605`
  (`develop`, PR #314's verified source branch).
- Optimized revision: `4939603d05ca8b233aa49f60844782e455bb03bd`.
- Apple M2 Max, 12 logical CPUs, 64 GiB system memory, macOS Darwin 25.6.0
  arm64; Node 24.19.0, npm CLI 11.17.0.
- Both revisions used isolated Git source archives with the same installed
  dependency tree. Source and installed lockfile digests are retained in the
  measurement data. There were no generated build outputs in either archive.
- This controls dependencies to isolate source changes. The release lockfiles
  differ in 22 dependency versions, including `brace-expansion`, `js-yaml`,
  `fast-uri`, and npm's bundled dependencies. This is not a comparison of two
  complete installations from their respective release lockfiles.

Commands and fixture generators are in the
[benchmark instructions](../../scripts/benchmarks/README.md). Workloads ran
sequentially, with no other test suite or benchmark running concurrently.
All reported ranges are minimum–maximum across repeated samples, not confidence
intervals. OS filesystem caches were not flushed. Fixture generation happens
before timing and warms the filesystem.

[Raw measurements](../../scripts/benchmarks/results/4.5.0.json) retain all
samples, outcomes, instrumentation, environment metadata, and exploratory
resolver runs. Temporary source/checkout paths are replaced with labeled
placeholders; timing values and fixture/content digests are unchanged.

## Story audits: additional correctness has a cost

The fixture contains 800 files split equally among JS, TS, JSX, and TSX, with
100 files in each of eight render/metadata cases. It includes shared helpers,
modern and legacy renders, inherited and overridden renders, explicit export
exclusions, and lexical shadowing. Consumer modules are only read and parsed.

Five samples per revision and mode, milliseconds, **median (range)**:

| Workload                            |        v4.4.0 | Release before optimization |
| ----------------------------------- | ------------: | --------------------------: |
| Combined audit CLI, fresh process   | 741 (667–770) |               878 (828–894) |
| Combined audit API, warm process    | 589 (558–655) |               655 (632–715) |
| Twig story audit CLI, fresh process | 162 (154–182) |               316 (290–317) |
| Twig story audit API, warm process  |   99 (96–100) |               166 (165–169) |

The tools agree within each revision: the base reports 700 legacy findings,
and the release reports 300. The release removes 100 false positives each for
modern-only shared helpers, overridden default renders, excluded exports, and
lexically shadowed template identifiers. Findings hashes are stable across
CLI, warm API, and instrumented runs.

Untimed instrumentation records exactly 800 Babel parses in each release audit
pass, including the combined audit. The regex-based base records zero Babel
parses. There is no duplicate parsing to eliminate here. The release does more
precise analysis and takes longer on this fixture; these are different semantic
workloads. No story analyzer optimization was justified by these measurements.

Fresh-process CLI timing includes startup, imports, and JSON reporting. Warm
API timing excludes imports and a priming pass; combined audits still reset
their file-read cache and standalone audits reread the files each pass. Their
difference is not purely a filesystem-cache effect.

## Grouped Twig resolution

The fixture has 120 grouping directories across 40 branches and three levels.
It resolves an early match, a deepest/last match, and a missing reference 100
times each. A later duplicate verifies that the first matching template wins.
Each sample owns a new directory cache; the first lookup and 99 warm lookups
are measured separately. Instrumentation runs separately from timing.

The original implementation eagerly constructed every group's candidate paths
before testing the first candidate. The optimization yields candidates one
group at a time and stops construction at the first match. Directory discovery
remains complete and cached by the caller. Candidate order, filesystem probes,
lexical and real-path containment checks, and cache invalidation are preserved.
Both compilation and audits still use the same Node-safe resolver.

Seven samples per batch, milliseconds, **median (range)**:

| Workload / batch                    |           Before |        Optimized |
| ----------------------------------- | ---------------: | ---------------: |
| 100 early lookups / initial         |    105 (101–108) |       31 (31–33) |
| 100 early lookups / reverse order   |       94 (92–95) |       40 (34–84) |
| 100 late lookups / initial          |    779 (764–822) |    681 (646–704) |
| 100 late lookups / reverse order    |    652 (607–681) |    795 (781–831) |
| 100 missing lookups / initial       |    931 (874–969) |    682 (667–737) |
| 100 missing lookups / reverse order |    657 (623–710) |    916 (876–955) |
| Combined audit CLI / initial        | 1836 (1638–1884) | 1638 (1601–1784) |
| Combined audit CLI / reverse order  | 1684 (1619–1848) | 1721 (1597–1744) |

The initial batch ran before then after using an isolated tracked patch. Its
production resolver bytes match `4939603`. The repeat used the exact committed
SHAs, running optimized first and before second. The optimized early range
retains a sample with a 54 ms first lookup. The early benefit repeats in both
orders: **57–70% lower median total time**. The 99 warm early lookups fell from
95 to 23 ms initially and from 85 to 27 ms in the repeat. First-lookup medians
were 10.09 to 8.04 ms initially and 9.50 to 10.06 ms in the repeat, so the
benefit is clearest after directory discovery.

Late/missing changes reverse direction between batches. CLI ranges overlap and
its direction also reverses. These measurements do **not** establish a reliable
late/missing or whole-audit speedup. The balanced CLI fixture contains 100 early,
100 late, and 100 missing required references, so late/missing work dominates.

Untimed early-lookup instrumentation, per 100 calls:

| Work counter                      | Before | Optimized |
| --------------------------------- | -----: | --------: |
| `path.resolve` calls              | 66,760 |     7,260 |
| Flattened grouped arrays          |    100 |         0 |
| Entries in those flattened arrays | 60,000 |         0 |
| `statSync` calls                  |  1,200 |     1,200 |
| `realpathSync` calls              |    400 |       400 |
| `readdirSync` calls               |    121 |       121 |

Each visited group still constructs its small candidate array; zero flattened
entries does not mean zero allocations. Late/missing filesystem and path-call
counts are also unchanged. This identifies the early benefit as avoided path
construction, not fewer filesystem probes or measured heap savings.

Before and after produce identical microbenchmark target/outcome hashes and
identical full audit findings hashes, including exactly 100 genuinely missing
references. The base incorrectly reports all 300 references as unresolved and
has no shared grouped resolver; its faster CLI median of 176 ms (165–326) is
non-equivalent work, not a performance target for the corrected resolver.

## Accessibility: bounded concurrency trades time for resources

Five samples per mode, eight distinct story IDs per sample, all scanning the
same deterministic iframe with twelve cards. Each sample starts a fresh Node
worker and each real Pa11y check launches a fresh Chromium browser. Cap order
rotates between rounds. There is no browser reuse or synthetic scan delay.

Pa11y 9.1.1 used its actual nested Puppeteer 24.43.1 and axe-core 4.11.4, with
Chromium `124.0.6355.0` at `/opt/homebrew/bin/chromium` for both revisions.
The fixture is prewritten and identical; no Storybook build occurs in this
workload.

**Median (range)**, total runner duration and sampled browser-tree RSS:

| Revision / cap       |   Duration, seconds | Peak active checks | Peak browser RSS, GiB |
| -------------------- | ------------------: | -----------------: | --------------------: |
| v4.4.0 / unbounded   |    4.19 (4.00–5.04) |                  8 |      6.01 (5.98–6.14) |
| Release / 1          | 11.53 (11.50–11.76) |                  1 |      0.80 (0.79–0.80) |
| Release / 2, default |    6.08 (5.94–6.21) |                  2 |      1.56 (1.54–1.57) |
| Release / 4          |    4.96 (4.58–5.27) |                  4 |      3.05 (3.00–3.09) |

All 160 checks completed with clean reports and no execution failures. The base
does not support configurable caps and is labeled unbounded. The default cap
of 2 takes about 45% longer than the base here while showing about 74% lower
sampled browser-tree RSS. This supports a resource-management tradeoff on this
machine; it does not establish a speed or reliability improvement in general.
The default remains 2.

Browser RSS sums launched Chromium roots and their descendants sampled every
200 ms, excluding Node. Shared pages can be counted more than once, and sampling
can miss short-lived or reparented processes. This is not proportional set size
or a precise peak allocation measurement. Sampling overhead is included in
timings and recorded separately. Raw data also retains worker startup/cleanup
wall time, individual check outcomes, report counts, and memory samples.

## Scope and limitations

The optimization changes only grouped candidate construction. It adds no
dependencies, new process-global caches, concurrency defaults, or public report
fields. It does not reduce directory discovery or filesystem probe counts.
Late matches and misses still search all eligible groups. Runtime compilation
already has a separate resolution cache, so repeated calls served by that cache
do not exercise this optimization.

Validation passed: seven new deterministic resolver regression tests, and the
broader run of **536 tests in 41 suites with five snapshots**, covering audit
commands, the story analyzer, Twig compilation/runtime, and accessibility.
The new tests check early stopping, direct/BFS/code-point duplicate precedence,
root real-path probe scope, lexical/symlink containment, directory-cache reuse,
caller invalidation, and file deletion. No timing assertions are used.

```sh
node_modules/.bin/jest --config config/jest.config.js --runInBand --coverage=false \
  config/vite/utils/twig-component-resolver.test.js scripts/audit \
  scripts/audit-twig-stories.test.js config/vite/plugins/twig \
  src/storybook/twig scripts/a11y.test.js
npm run lint
```

Changed files were formatted with the repository's Prettier configuration;
commit hooks also ran lint and commit-message validation. Benchmark source,
tests, and methodology are committed separately from these measurements so the
optimized implementation has an exact, independently testable SHA.

These are small local samples of synthetic but deterministic developer
workloads. Large story bodies, different grouping layouts, consumer extensions,
slower disks, and other browsers can change the balance. No wall-clock assertions
were added to ordinary CI. Allocation counters describe candidate entries,
not retained JavaScript heap. No audit result is used to claim a general
Storybook or production-build speedup.
