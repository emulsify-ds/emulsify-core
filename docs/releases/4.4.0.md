# Emulsify Core 4.4.0

Emulsify Core 4.4.0 is a minor release focused on reliable asset resolution,
actionable build diagnostics, and stable incremental output. It resolves more
CSS `url()` forms across Drupal, WordPress, `none`, legacy, and customized
project structures while keeping `dist/` self-contained by default.

No consumer migration is required for the default path, and the public package
exports are unchanged. For detailed configuration and operational guidance,
see:

- [Asset References](../asset-references.md)
- [Project Structure And Output](../project-structure.md)
- [Project Audit](../audit.md)
- [Develop Reporter](../develop-reporter.md)
- [Release Verification](../release.md)

## Why This Is A Minor Release

The asset work separates URL resolution from output placement. Resolving an
authored URL that previously broke is an additive correction; making CSS reach
outside `dist/` would change an established deployment contract. The latter is
therefore opt-in:

> The `dist/` contract change is opt-in behind
> `assets.selfContainedOutput`; the default path preserves 4.3.2's deployment
> contract and additionally resolves `url()` forms that were broken in 4.3.2.

Projects that deploy only `dist/` keep doing so. Projects that deploy the whole
theme can choose a leaner, non-self-contained output. This makes 4.4.0's default
behavior backward compatible while adding new resolution capabilities.

## CSS Asset Resolution

Sass and CSS now accept `@assets/...` as a first-class alias equivalent to
`/assets/...`. Both spellings resolve against the normalized project asset
roots, produce the same emitted URL, and are not reported as repairs. The
stylesheet namespace is reserved ahead of consumer Vite aliases and package
resolution. When Vite cannot resolve a legacy bare or wrong-depth stylesheet
URL, Emulsify repairs it only when exactly one file matches. Together, this
covers:

- first-class `/assets/...` and `@assets/...` URLs, including configured
  `assets.roots`;
- legacy bare `assets/...` URLs;
- relative URLs whose depth suited one emitted project shape but not another;
- the default `assets/` and `src/assets/` roots; and
- query strings, fragments, combined `?query#fragment` suffixes, whitespace
  inside `url( ... )`, and quoted URLs containing `)`.

Query strings and fragments are kept out of the asset lookup and reattached to
the final relative URL. CSS comments, line comments, and quoted string values
are not treated as live `url()` tokens. Existing source-relative URLs are left
alone, including when a component-local file has the same tail as a project
asset. Directories never count as resolved files.

### Output Placement

`assets.selfContainedOutput` defaults to `true`. Resolved assets remain or are
emitted under `dist/assets/`, and final CSS points at those copies at the depth
required by its emitted location. The output directory therefore remains a
deployable unit.

Projects that deploy the complete theme can opt into source-tree references:

```json
{
  "assets": {
    "selfContainedOutput": false
  }
}
```

In that mode, Emulsify removes an output copy only when a corresponding emitted
CSS URL has been redirected successfully. Copies still required by JavaScript,
HTML, or another output remain available. Set
`EMULSIFY_SELF_CONTAINED_OUTPUT=0` for the same one-build override; `false`,
`off`, and `no` are also accepted.

`assets.rebase: false` and `EMULSIFY_ASSET_REBASE=0` are end-to-end escape
hatches. They disable `@assets/...` normalization, legacy repair, and final
relativization and keep Vite's copies, so a maintainer can bisect unexpected
behavior without a second output setting changing the result.

### Strict Builds And Storybook

Set `EMULSIFY_STRICT_ASSETS=1` to fail on unresolved stylesheet asset URLs, or
`=2` to also fail when Emulsify had to repair a URL. Strict failures now list
each offending URL with its importer, preserve distinct occurrences in
different stylesheets, and use wording that distinguishes unresolved URLs from
successful repairs. Invalid strictness values warn instead of silently
selecting a weaker level. Valid `/assets/...` and `@assets/...` references do
not count as repairs at either level.

Storybook builds capture the same Vite notices even though Storybook resolves
the shared configuration with `command: 'serve'`. Twig `source()` public asset
URLs are relative to the preview document, so static Storybook builds work at
a domain root or deployment subpath. Generated `dist/assets` lookup is limited
to the generated sprite alias rather than inlining every copied project asset
again.

## Project Audit And Safe Fixes

`emulsify-audit` now checks both first-class asset aliases and can apply
unambiguous repairs to legacy bare or wrong-depth forms with `--fix`. It leaves
valid `@assets/...` URLs unchanged and uses `/assets/...` as the stable autofix
output. Its CSS scanner shares the build's comment-and-string policy, so the
audit never offers a fix for a token the build would ignore. Sass interpolation
receives manual guidance instead of a malformed rewrite or a false automatic-fix
promise.

Source rewriting is hardened for consumer files:

- non-UTF-8 files are skipped with a warning instead of being corrupted;
- writes use a byte-bounded same-directory temporary file and atomic rename;
- symlinks resolving outside the scanned project root are skipped;
- per-file I/O failures are skipped without abandoning later files;
- interrupted-run temp files are cleaned on exit or the next fix run; and
- post-fix text and JSON reports contain only findings that remain.

Atomic rename preserves mode and ownership but replaces the target inode.
Hardlinked aliases therefore retain the old bytes, and a mode-read-only POSIX
file can still be replaced when its parent directory is writable.

Working component-relative asset references are informational at most and are
never rewritten to a different root-level file.

## Incremental Builds And Reporting

Watch builds empty the output on their first cycle, then update it
incrementally. Unchanged files are compared in chunks and are not rewritten,
which avoids unnecessary Storybook reloads. File create and delete events
refresh the copy plan, but later cycles do not prune stale copied output.
Destinations inside the emptied output directory are reconciled on restart or a
one-shot build; Drupal SDC output mirrored outside it may require manual cleanup
after a component delete or rename.

Persistent output is also hardened against unsafe destinations and quiet
failures. A destination symlink is replaced with a real output file without
writing through to its target. Copy failures are reported with the affected
path and error code and count as cycle failures rather than leaving stale bytes
behind a green build.

The reporter now:

- reports unresolved CSS assets in one-shot builds;
- uses one failure verdict for first builds and rebuilds, including missing
  imports and malformed build-error entries;
- keeps meaningful Vite and esbuild code frames while compacting duplicated
  Sass frames;
- preserves each importer for repeated broken URLs; and
- prints collected Sass deprecations at the end of a standalone
  `storybook build`.

## Package And Runtime Updates

The supported consumer floor remains Node.js 24.13.0. Contributors use the
24.18.0 version pinned in `.nvmrc`, and release-readiness CI exercises both
versions.

These bundled runtime dependencies moved within their existing major versions:

| Dependency  | 4.3.2 range | 4.4.0 range |
| ----------- | ----------- | ----------- |
| `vite`      | `^8.1.5`    | `^8.2.1`    |
| `storybook` | `^10.5.4`   | `^10.5.8`   |
| `js-yaml`   | `^5.2.2`    | `^5.3.0`    |
| `axe-core`  | `^4.12.1`   | `^4.13.0`   |
| `postcss`   | `^8.5.23`   | `^8.5.26`   |

The package manifest test now verifies npm's actual ordered `files` evaluation,
so audit tests and other excluded internals cannot leak into the tarball through
misordered negation patterns.

Production entry discovery continues to compile `*.doc.js`, `*.docs.js`, and
their JSX equivalents for compatibility. Story files, component metadata,
pre-minified bundles, and tests remain excluded from production entries.

## Release Publication

Semantic-release publishes the version already committed by the develop
version workflow. The release configuration deliberately does not use
`@semantic-release/changelog` or `@semantic-release/git`, avoiding a second
version commit. The generated GitHub Release is the only changelog; this
repository does not maintain a `CHANGELOG.md` file.

Package publication requires npm provenance through
`package.json#publishConfig`. Supplying `NPM_TOKEN` cannot silently downgrade a
release to an unattested publish: npm must create provenance or publication
fails.

At release-preparation time,
[`@emulsify/core@4.4.0` on npm](https://www.npmjs.com/package/@emulsify/core/v/4.4.0)
is not yet published, so its provenance badge cannot be checked before merge.
After the publish workflow succeeds, maintainers must confirm:

1. npm lists `@emulsify/core` version 4.4.0 and displays its provenance badge;
2. the `v4.4.0` Git tag points at the validated `main` commit; and
3. the GitHub Release exists and contains the generated release notes.

## Migration Actions

None are required for existing projects using the default self-contained
output. After upgrading:

1. keep Node.js at 24.13.0 or later;
2. run `npx --no-install emulsify-audit` to identify source URLs worth
   canonicalizing;
3. run the project's build and Storybook build; and
4. choose `assets.selfContainedOutput: false` only when deployment includes the
   complete theme and every configured asset root.

From a clean Core checkout, release verification remains:

```sh
npm ci
npm run release:verify
```
