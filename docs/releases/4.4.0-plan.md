# Emulsify Core 4.4.0 — Plan

Status: implemented on `develop`. Primary theme is the `npm run develop`
reporting experience. User-facing documentation lives in
[Develop Reporter](../develop-reporter.md); this document records the reasoning
and the source-level findings behind the change.

4.3.0 introduced the develop reporter. It replaced Sass's per-occurrence
deprecation blocks and Rolldown's aggregate failure dumps with a banner, one
summary per cycle, and one line per rebuild. That part works. What 4.3.0 did
not do is stop the _other_ participants in `develop` from talking, so the
reporter's clean summary lands in the middle of roughly a hundred lines of
foreign output and scrolls away.

4.4.0 finishes the job: one `develop` run should read as one tool.

## The problem, by source

A representative `develop` run on a real consumer theme emits ~112 lines before
the first rebuild. They come from five different producers:

| Lines | Producer                                                      | Channel                   |
| ----- | ------------------------------------------------------------- | ------------------------- |
| 7     | npm script echo, nested through `concurrently`                | consumer's own scripts    |
| 5     | Vite JS build chatter                                         | `config.logger.info`      |
| ~4    | Rolldown progress (`transforming (N)`, `modules transformed`) | Rust → stdout direct      |
| ~78   | Rolldown asset table + `computing gzip size...`               | Rust → `logInfo` callback |
| 8     | Storybook's boxed `Storybook ready!` banner                   | `@clack/prompts` box      |
| ~10   | Emulsify reporter                                             | direct stdout             |

The reporter is 9% of its own output.

### Why the current suppression does not work

`config/vite/vite.config.js` supplies a `customLogger` and its comment asserts
that `config.logLevel` "cannot do this job" because Vite ignores the level when
a custom logger is present. That is true of `createLogger`, and false of the
thing that actually matters.

Vite's build reporter reads `config.logLevel` directly and independently of the
logger (`node_modules/vite/dist/node/chunks/node.js:3251`):

```js
const shouldLogInfo = LogLevels[config.logLevel || "info"] >= LogLevels.info;
// ...
logInfo: shouldLogInfo ? (msg) => env.logger.info(msg) : void 0,
```

That flag crosses into Rolldown's native plugin, whose Rust
`register_hook_usage` keys off whether `log_info` is present:

```rust
if self.log_info.is_some() {
  usage |= HookUsage::Transform | HookUsage::BuildStart | HookUsage::BuildEnd
        | HookUsage::RenderChunk | HookUsage::WriteBundle;
  if self.is_tty { usage |= HookUsage::GenerateBundle; }
}
```

Two consequences the current config misses:

1. **Rolldown's progress lines never touch the JS logger.** They are written
   from Rust with `write_line`, which emits `\x1b[2K\r` and no trailing
   newline. That is the mechanism behind the garbled
   `transforming (39) …│ Storybook ready!` collisions under `concurrently` — a
   carriage-return rewrite on a stream shared with another process. No
   `customLogger` can intercept it.
2. **`logLevel: 'warn'` un-registers the hooks entirely.** Rolldown then never
   instruments transforms, never walks the chunk graph for the report, and
   never computes gzip sizes. This is a correctness fix _and_ a per-rebuild
   performance win.

Corollary: `build.reportCompressedSize: false` is not needed. It suppresses only
the `computing gzip size...` line and the `│ gzip:` column; the table itself is
gated by `logInfo`. Once `logLevel` is set it is dead weight.

## Phase 1 — Silence everything Emulsify does not own

Append-only. No new process management. No consumer-facing API change.

**`config/vite/vite.config.js`**

- Add `logLevel: watching && !isVerbose() ? 'warn' : 'info'` to the base config.
  This is the load-bearing change.
- Keep the `customLogger` at `warn` (already staged in the working tree). It
  covers the five JS-side messages: `vite vX building … for production...`
  (`node.js:33018`), `watching for file changes...` (33025), `build started...`
  (33043), `built in Nms.` (33047), `✓ built in <t>` (33063).
- Replace the `logLevel cannot do this job` comment with the correct account of
  the two switches. The comment is currently the reason nobody reached for the
  working lever.
- Gate both on `EMULSIFY_VERBOSE` so the raw firehose stays one env var away.

Expected result: the ~82 Rolldown lines and 5 Vite lines go to zero.

## Phase 2 — Fold Storybook into the reporter's voice

`renderReady()` already exists in `config/vite/plugins/reporter/render.js` and
has **zero call sites** — it is staged but unwired. It renders a ready state in
the reporter's vocabulary, including a `portDrift` case.

Storybook's box comes from `outputStartupInformation()`
(`node_modules/storybook/dist/core-server/index.js:11399`), called at 12023
behind exactly one guard:

```js
options.quiet || outputStartupInformation({ … });
```

Two ways to wire it, in preference order:

**2a. Intercept `logBox` (recommended).** Wrap `logger.logBox` from
`storybook/internal/node-logger` as a module side effect at the top of
`.storybook/main.js`. `main.js` is itself a Storybook preset and is evaluated
during `loadAllPresets`, well before line 12023 runs. Parse the local/network
URLs out of the box payload and hand them to `renderReady()`.

- Requires no change to any consumer's `develop` script — decisive for a minor
  release.
- Gets the _actual_ bound port for free, which is the only reliable source for
  the `portDrift` warning. Consumers run `storybook dev --ci`, and `--ci` makes
  Storybook silently fall forward to the next free port
  (`core-server/index.js:11889`) — meaning today a stale session on 6006 sends
  you to a browser tab showing the wrong instance with no warning.
- Depends on the `storybook/internal/*` subpath. Wrap in try/catch: if the
  import or the shape changes, do nothing and let Storybook print its own box.
  Degradation is cosmetic.

**2b. `--quiet` plus our own print.** Surgical — `--quiet` suppresses exactly
the box, the manager/preview timing line, and one `Starting...` info line. But
it requires every consumer to edit their `storybook` script, and it leaves us
without the resolved port. Note `--quiet` also leaves the clack intro line
`storybook v10.5.5` (`dist/bin/core.js:3951`), which only `--loglevel warn`
removes — and that would mute Storybook's genuine warnings too.

Also worth confirming: `--ci` suppresses nothing. It only skips the browser
open and the port prompt.

## Phase 3 — Summary shape

**Decided: C2, the half-block panel.** Wordmark retained, an aligned key-value
facts block carrying `platform` / `input` / `output`, a framed URL panel, then
problems ordered by whether you can act on them.

### Banner and summary split

The banner fires at `configResolved`, which is before the build. It can know
`input` but not `output` — file count and total bytes only exist at
`writeBundle`. Rather than split the facts across two moments, move the whole
facts block into `renderSummary()` and reduce `renderBanner()` to the wordmark
plus `core <version>`. The banner's stated job is marking where Emulsify's
output begins, and it still does that.

`renderBanner()` therefore loses `platform` and `entryCount`; both move into the
facts block. This is the change that breaks the three banner tests listed below.

### Facts block

```text
      platform    Drupal
      input       src/components/   28 entries
                  src/layout/        6 entries
                  src/foundation/    5 entries
      output      dist/  41 files · 2.3 MB · largest style.css 388 kB
```

The `input` rows are the most valuable addition in this release. "Is Emulsify
actually seeing my folders" is the first question on any misconfigured project
and nothing in the current output answers it.

The data is already resolved — this costs no new filesystem work:

- `resolveProjectStructure()` returns `sourceRootRecords` as `{name, directory}`
  pairs (`config/vite/project-structure.js`), assembled from
  `componentRootRecords` plus `globalRootRecords`.
- When `variant.structureImplementations` is set in `project.emulsify.json`,
  those named roots _are_ the component roots verbatim
  (`project-structure.js:250-263`), so the rows come straight from config:
  `components → ./src/components/`, `layout → ./src/layout/`, and so on.
- Without it, `fallbackComponentRoots` and `fallbackGlobalRoots` supply
  `src/components` (or root `./components`) plus the global root.
- Per-root entry counts come from bucketing the existing entry map through
  `findSourceRoot(absPath, roots)`, which already exists in the same module.

Render each root relative to the project root with a trailing slash, in
`sourceRootRecords` order so configured structure order is preserved.

`output` replaces the discarded 78-line table with the one signal worth keeping.
`writeBundle(options, bundle)` receives every output file; file count, total
bytes, and the largest asset are three lines of reduction.

### URL panel

The URLs are framed in the wordmark's own glyph vocabulary rather than
box-drawing characters, so the block reads as Emulsify instead of as a second
tool's box:

```text
  ▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄
    storybook   http://localhost:6007/
    network     http://192.168.1.25:6007/
  ▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀▀
```

- This is the first call site for `renderReady()`. Extend it with the panel
  treatment and keep the `portDrift` branch, which should tint the rules yellow
  and add the drift fact rather than printing a separate warning.
- Gate the glyphs on the existing `supportsUnicode()` in `format.js` — the same
  switch the wordmark uses, so a terminal gets either both or neither. When it
  returns false, degrade to plain label rows with no rules.
- Measure the panel width from the longest rendered row rather than hardcoding
  it, so a long network address or an added row cannot overflow the rules.
  Measure before styling; ANSI escapes would skew the width, which is the trap
  the existing column code already documents.

### Problem ordering

Two labelled dividers, actionable first:

```text
  ── needs attention ─────────────────────────────────
  ── pre-existing debt ───────────────────────────────
```

`needs attention` carries syntax errors, import errors, plain errors, warnings,
and unresolved asset URLs. `pre-existing debt` carries Sass deprecations,
collapsed to the total, the file count, and the one migrator command plus how
many occurrences it fixes.

Suppress a divider entirely when its section is empty. A clean run should not
advertise the categories it has nothing to put in.

## Phase 4 — The consumer `develop` script

The remaining 7 lines are npm's own script echo from `concurrently` spawning
nested `npm run` calls. Emulsify owns the recommended script in two places:

- `.github/fixtures/consumer/whisk-drupal/package.json:14`
- `docs/migration-4x.md:152`

Update both to quiet the nested npm invocations, and document the change in the
release notes as optional — existing scripts keep working, they just stay noisy.

  `supportsUnicode() === false`, width measured from the longest row, and the
  `portDrift` branch.

  import is unavailable.
- Write tally reduction over a synthetic `writeBundle` bundle.
- Facts block `input` rows in three shapes: explicit
  `variant.structureImplementations`, `src/components` fallback, and root
  `./components` fallback. Assert per-root entry counts sum to the total entry
  count, and that root order follows `sourceRootRecords`.
- Divider suppression when a section is empty.

## Other 4.4.0 candidates

- **Stale JSDoc in `config/vite/plugins/reporter/diagnostics.js:145-157`** — the
  documented `snapshot()` shape omits `syntaxErrors`, which the implementation
  returns. Cheap fix while the file is open.
- **`docs/` entry for the reporter** — there is no page describing the develop
  reporter, its env vars (`EMULSIFY_VERBOSE`, `EMULSIFY_NO_UNICODE`,
  `NO_COLOR`, `FORCE_COLOR`), or how to read the summary blocks. If 4.4.0 is
  the reporting release, it should ship the doc.
- **Reporter package-file coverage** — confirm the new/renamed reporter modules
  are all listed in `package.json` `files`, and that `config/package-exports.test.js`
  and `config/consumer-contract.test.js` cover them.

## Verification

Beyond `npm run release:verify`, this release needs a manual check that unit
tests cannot make: run `develop` in a real consumer theme and confirm the
output. Specifically confirm:

- No `\x1b[2K\r` fragments survive under `concurrently`.
- A stale Storybook holding the requested port produces the `portDrift`
  warning rather than a silent fall-forward.
- `EMULSIFY_VERBOSE=1` still restores the full raw stream.
- The panel rules align with the longest URL row, and degrade cleanly with
  `EMULSIFY_NO_UNICODE=1` and under `NO_COLOR=1`.
- `input` rows match the project's actual structure on at least one
  `structureImplementations` project and one `src/components` project. The
  release fixtures at `.github/fixtures/release/structure-implementations` and
  `.github/fixtures/release/no-platform-src-components` cover both.
