# Emulsify Core 4.5.0

Emulsify Core 4.5.0 adds an optional WCAG 2.2 preset for Pa11y and bounds
accessibility scans to two concurrent browsers by default. It also refreshes
compatible security dependencies, verifies copied audit wrappers, and records
current Twig/PHP serialization differences without changing those outputs.

## Why This Is A Minor Release

The reusable `@emulsify/core/a11y/wcag22` preset is a new public package
export. Consumers choose whether to import it; the existing default Pa11y
rule selection and configuration merge behavior remain unchanged. The
concurrency adjustment is resource scheduling, and the other changes are
corrections, documentation, or verification.

No dependency changes major. The supported Node.js floor remains 24.13.0,
the recommended version remains 24.18.0, and React/React DOM 18 and 19 remain
supported. Existing `dist/` paths, BEM classes, SVG fragment IDs, component
templates, and copied-script entry points are preserved.

## Optional Accessibility Preset

Opt in from `config/emulsify-core/a11y.config.js`:

```js
import wcag22 from '@emulsify/core/a11y/wcag22';

export default wcag22;
```

Projects with existing overrides should retain their settings and merge the
preset's `pa11y` options as shown in the
[accessibility guide](../accessibility.md). The preset explicitly enables
`target-size`, the WCAG 2.2 A/AA rule supported by the reviewed axe version,
through Pa11y's existing `rules` API. Storybook already requested WCAG 2.2
checks; this closes a difference in automated rule selection.

The packaged fixture demonstrates that adjacent 10-pixel buttons fail with
the preset and corrected 24-pixel targets pass, while default selection
remains unchanged. This is evidence of a testing gap, not a finding about a
shipped Core component. Review [SC 2.5.8 and its exceptions](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)
in context. Automated rules do not establish complete WCAG conformance.

## Bounded Accessibility Scans

The accessibility runner checks every configured and discovered story with
at most two Pa11y checks active at a time. An optional positive integer
`concurrency` in the project accessibility configuration changes that cap.
Reports remain in input order, and failed checks are drained before the
temporary Storybook server closes. Findings and failed checks still produce
exit status 1. The [developer workload measurements](4.5.0-performance.md)
describe their specific environments and limits; they do not establish a
general speed or memory guarantee.

## Security Dependencies

Compatible updates remove the reviewed `brace-expansion`, `fast-uri`, and
nested `js-yaml` advisory ranges. Updating the development-only npm bundle
also clears its affected bundled packages. The September 9 refresh additionally
updates locked `colord` from 2.9.3 to compatible 2.10.0. The dated
[dependency assessment](../security-4.5.0.md) retains the exact Core and
fresh-consumer audit results and residual `extract-zip` advisories in the
Pa11y browser-installation chain. That assessment supersedes the earlier
checkpoint's advisory counts.

Consumers must refresh their own lockfiles; Core's lockfile does not replace
a theme's locked transitives. Run the theme's security audit and build
checks after refreshing. The [security review](../security-4.5.0.md) records
actual browser-installation exposure and the unresolved owner, acceptance,
and review-date decisions. An optional managed-browser configuration was tested
to avoid Puppeteer's browser download/extraction path; it leaves the dependency
findings visible. Pa11y 10 is not forced into this release.

## Copied Audit Wrappers

Existing themes whose audit wrapper prints a documentation footer to stdout
must add `>&2` to that footer when using JSON output. Preserve the audit
command's exit status. Use `npm run --silent audit -- --json` to also omit
npm's command echo, or call `npx --no-install emulsify-audit --json` directly.
The [before/after migration example](../migration-4x.md#manual-packagejson-updates)
shows the small local edit. No theme regeneration is required.

The packed Drupal consumer checks the combined and Twig-only wrappers: the
entire stdout must be one JSON document, documentation footers go to stderr,
and success and failing-threshold exit statuses survive. Source paths with
spaces and quotes exercise argument forwarding. Starter tests also exercise
their actual generated manifests with an installed Core package and reject
the old stdout footer and a wrapper that masks failure. Core's audit JSON
shape is unchanged.
Later corrections in the release range classify shared Twig helpers per
render path and honor statically readable Storybook export selection. The
[September 8 review record](4.5.0-verification.md#open-audit-findings-kept-outside-this-sprint)
preserves the original findings and that checkpoint's scope decision; it is
not a list of currently unresolved classifier defects.

### Starter Availability

Starter availability is separate from the Core package version. The following
status was checked on September 9, 2026; a local commit alone is not evidence
of a published starter fix.

- **Drupal:** the correction in `87016d0` is present on `main` and included in
  [7.2.2](https://github.com/emulsify-ds/emulsify-drupal/releases/tag/7.2.2).
  Themes generated from that release receive both corrected wrappers.
  Additional generated-consumer tests and migration guidance are pushed on
  `codex/test-generated-audit-wrappers` in
  [draft PR #380](https://github.com/emulsify-ds/emulsify-drupal/pull/380);
  that follow-up is not merged or released.
- **WordPress:** the current
  [2.0.0 release](https://github.com/emulsify-ds/emulsify-wordpress/releases/tag/2.0.0)
  retains the stdout footer. The historical local fix `a34d7ec` was not on
  the remote starter branches at inspection. The correction and generated
  consumer tests are now pushed on `codex/audit-wrapper-json-contract` in
  [draft PR #42](https://github.com/emulsify-ds/emulsify-wordpress/pull/42),
  based on `main`. They are not merged or released; themes generated from
  the current release still need the manual edit.

Existing Drupal and WordPress themes still need the
[small manual wrapper edit](../migration-4x.md#manual-packagejson-updates),
or can invoke the installed audit executables directly. Updating Core does
not replace a theme's copied npm scripts.

## Compatibility Evidence And Repository Operations

A versioned corpus records current JavaScript and pinned Emulsify
Tools PHP output, including object BEM argument order, utility-class
punctuation, boolean overrides, ARIA list merging, escaping, and context
consumption. It documents the portable subset and known divergences. No
helper output is harmonized, and PHP remains an optional maintainer check.

Both `develop` and `main` use the
[registered CI checks](../release.md#required-ci-checks). Existing
administrator bypass and other protection settings are preserved. Workflow
actions are pinned to verified commit SHAs with weekly Dependabot updates.
Superseded pull-request validation is cancelled; integration pushes have
distinct concurrency groups. The publish workflow retains its validation
barrier and publication policy.

The preview-head override was verified against published Core 4.4.0 before
issue #80 was closed. The absent `imagemin-gifsicle` dependency was similarly
verified before issue #157 was closed. Drupal-filter and performance
documentation now describe the existing opt-in and fixture byte ceiling.

Release verification now generates ignored, revision-specific evidence rather
than requiring test and fixture totals to be copied into prose. Local
`npm run release:verify` writes `.release-evidence/report.json`; CI retains
per-job `release-evidence-...` artifacts. The
[report guide](../release.md#generated-evidence-for-the-checked-revision)
explains source identity, partial or unavailable results, and the distinction
between execution evidence and release approval.

## Migration Actions

1. Refresh the consuming theme's compatible dependency lockfile, then run
   `npm audit` and the project's checks.
2. Import the WCAG 2.2 preset only if the additional automated check is wanted.
3. Add `>&2` to a copied audit footer that currently contaminates JSON stdout,
   or invoke the audit executable directly.

An existing supported 4.x consumer needs no regeneration, runtime change,
configuration migration, or template/class changes. A consumer upgrading
from 4.2 on Node.js below 24.13.0 still encounters the historical 4.3.0 floor
increase; 4.5.0 adds no further increase.

## Release Publication

Publication remains the separate automated workflow after an authorized merge
to `main`. The [maintainer decision register](../maintainer-decisions.md)
separates immediate release decisions from proposed follow-ups. Passing the
checks does not approve risk acceptance or resolve those decisions.
