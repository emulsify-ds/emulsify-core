# Emulsify Core 4.5.0

Emulsify Core 4.5.0 makes developer audits more accurate and accessibility
runs more useful when individual browser checks fail. It adds an optional
WCAG 2.2 target-size preset, bounds concurrent accessibility checks, fixes
Twig story and template-reference findings, and updates compatible security
dependencies. The supported authoring APIs, classes, and output paths remain
unchanged. Incorrect bare Twig references that previously selected another
group's component must be corrected as described below.

These notes cover the complete unreleased change from `v4.4.0` to PR #314,
including work already on `develop` before release preparation. Publication
and human approval remain pending; the
[release assessment](4.5.0-assessment.md) identifies the reviewed revisions,
verification evidence, and outstanding decisions. Its September 10 readiness
conclusion is superseded by the later dependency refresh and September 11
corrections. Earlier security, benchmark, parity, and CI results remain scoped
to their recorded revisions; they do not establish verification of the final
dependency tree or release head.

## Why This Is A Minor Release

The reusable `@emulsify/core/a11y/wcag22` preset is the only new public
package export. Consumers choose whether to import it; the existing default
Pa11y rule selection and configuration merge behavior remain unchanged.
No public exports are removed. The shared component resolver is packaged
internal code, not a new supported import path. Storybook's existing public
render helpers and custom-element APIs are unchanged from 4.4.0.

There are no dependency major-range upgrades. The audit adds a declared
`@babel/parser` dependency. The supported Node.js floor remains 24.13.0,
the recommended version remains 24.18.0, and React/React DOM 18 and 19 remain
supported. Existing `dist/` paths, BEM classes, SVG fragment IDs, component
templates, and copied-script entry points are preserved.

## Optional Accessibility Preset

Opt in from `config/emulsify-core/a11y.config.js`:

```js
import wcag22 from '@emulsify/core/a11y/wcag22';

export default wcag22;
```

Projects with existing overrides should retain their settings and merge the
preset's `pa11y` options as shown in the
[accessibility guide](../accessibility.md). The preset explicitly enables
`target-size` through Pa11y's existing `rules` API. Storybook already requested
WCAG 2.2 checks; this closes a difference in automated rule selection.

The packaged fixture demonstrates that adjacent 10-pixel buttons fail with
the preset and corrected 24-pixel targets pass, while default selection
remains unchanged. This is evidence of a testing gap, not a finding about a
shipped Core component. Review [SC 2.5.8 and its exceptions](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)
in context. Automated rules do not establish complete WCAG conformance.

## Accessibility Results And Concurrency

The runner attempts each selected story once, with at most two Pa11y checks
active at a time by default. An optional positive integer
[`concurrency`](../extension-points.md#accessibility-scan-concurrency) in the
project accessibility configuration changes that cap.

Completed reports remain visible even when another check fails; every
execution failure identifies its story and URL. Reports and errors appear in
input order after the workers settle, before the temporary Storybook server
closes. The summary separates attempted stories, clean reports, reports with
findings, and failed executions after the existing ignore/filter logic.
Reportable findings and execution failures retain a nonzero exit status;
programmatic execution failures are aggregated after reporting.

The default cap controls browser resources. In the recorded eight-story
benchmark, cap two used about 74% less sampled browser-process-tree RSS than
the prior unbounded runner and took about 45% longer. This is a workload and
machine-specific tradeoff, not a general speedup or memory guarantee. See the
[measurements and sampling limitations](4.5.0-performance.md).

## More Accurate Twig Audits

The combined audit and Twig story audit classify each selected story's
effective render path. A modern `renderTwig(Template)` story no longer hides
a separate legacy `Template.bind({})` story using the same helper. Modern
composed stories remain recognized, with support for local aliases, bound
functions, object renders, and lexical shadowing.

Story selection follows the supported static CSF export rules instead of
capitalization. Lowercase stories are checked; string-array and regular-expression
`includeStories`/`excludeStories` filters can exclude helper exports. Metadata
aliases and supported TypeScript wrappers are read without executing project
code. Default renders are considered only when a selected story uses them,
and story overrides take precedence.

Template-reference checks now share the runtime's existing grouped-component
resolver. For example, a Drupal SDC reference `example:footer` can resolve to
`src/components/navigation/footer/footer.twig`. Deeper grouping levels work
with the same deterministic duplicate-name precedence as compilation. Configured
namespaces, non-SDC projects, and `@assets/...` source references remain supported.
Both build-time and audit resolution now preserve every segment of a bare path:
`atoms/button` or `atoms/button/button.twig` cannot silently resolve
`molecules/button/button.twig` when `atoms` is missing. This intentionally fixes
erroneous runtime fallback behavior. Configured namespace paths and explicit
`project:button` or `@project/button` shorthand retain grouped lookup.

The structured scanner checks complete static `include()` and `source()`
arguments, ignores Twig comments and unrelated context strings, and preserves
source lines. String fragments in concatenation or interpolation are not
independent references. An include fallback array is satisfied when an eligible
candidate resolves; a required all-static, all-missing call still warns once.
Supported explicit ignore-missing arguments, including
`source('optional.twig', true)`, do not produce a required-reference warning.

Static missing templates are still checked when the variables argument is an
identifier, member expression, filtered expression, or object containing numeric
keys. For example, `include('@components/missing.twig', item)` warns just as the
same call without a variables bag does. An unreadable variables bag does not
make a required call optional. An explicit unreadable ignore-missing flag remains
unknown, and an explicit `true` remains optional, with the existing option
precedence preserved.

Dynamic metadata, imported render implementations, and dynamic Twig candidates
cannot all be determined statically. The analyzer retains uncertainty rather
than executing consumer code or certifying those cases as modern/resolved.
Mixed static/dynamic fallback groups do not claim definitive failure. Native
Twig named arguments remain unknown, and `source()` arrays are not treated as
include fallbacks. Public audit interfaces, finding IDs, JSON shape, and default
thresholds are preserved; findings intentionally change where classification
was wrong. The [assessment](4.5.0-assessment.md#disposition-of-correctness-findings)
links the corrections to their commits and regression tests.

## Source Code Stays Out Of Copied Assets

PHP files colocated with frontend source, such as
`src/Hook/PageTitleHooks.php`, are no longer copied into `dist/global/` or
component output. The case-insensitive exclusion also covers PHP/Drupal
`.inc`, `.module`, `.theme`, `.install`, `.profile`, `.engine`, `.phtml`, and
`.php` with a single numeric suffix, plus modern JavaScript/TypeScript forms
such as `.mjs`, `.cjs`, `.ts`, `.tsx`, `.mts`, and `.cts`. These files are not
static assets or new build entries. The existing exclusions for JavaScript,
Sass, Twig, source maps, and component metadata continue to apply.

The rule applies to default and configured source roots on all platforms.
Directories containing only excluded code produce no copied output, and saving
that code does not trigger the static asset copier. Images, fonts, data files,
and custom asset extensions retain their copy and watch behavior; the copier
continues to use explicit code exclusions rather than an asset allowlist.

No source moves or configuration changes are required. Restart
`npm run develop` or run a fresh build after upgrading; Core's default output
cleaning removes previously copied source code under `dist/`. Consumers that
disable output cleaning must remove those stale generated copies themselves. See
[PHP alongside frontend files](../project-structure.md#php-alongside-frontend-files).

## Twig Cache Refresh And Group Discovery

The Twig plugin uses Vite 8's typed `hotUpdate` hook for template creation,
updates, and deletion. Each event reaches cache invalidation; creation and
deletion also clear grouped-directory discovery and cached misses. A previously
missing component can resolve after it is created, and a deleted component no
longer survives as a cached hit. Vite 8.3.0 is the declared minimum within the
supported Vite 8 range.

Grouping discovery shares the source walker's exclusions for `node_modules`,
`.git`, `.cache`, `.vite`, `.out`, `.coverage`, and `dist`. These directories
are not searched as component groups. Legitimate nested grouping remains
supported at any depth; there is no arbitrary depth cap. Duplicate precedence
remains breadth-first with UTF-16 code-unit ordering between sibling directories.

## Measured Resolver Improvement

The shared Node-safe resolver now creates grouped candidates lazily and stops
when a match is found. Directory discovery stays cached within the caller's
run. Grouped runtime support itself is not new in 4.5.0. The September 11
correctness and directory-discovery changes above are separate from the measured
candidate-construction optimization.

In two batches of seven samples, 100 early grouped lookups had 57–70% lower
median duration after this optimization, with identical outcomes and filesystem
probe counts. Late and missing lookups and whole-audit timings did not show a
consistent improvement. More precise story analysis took longer than 4.4.0 on
the recorded fixture and produced different, corrected findings. These
[controlled source measurements](4.5.0-performance.md) compare `e9e701cc` and
`4939603` on September 9. They do not measure the later `fbbc6b9` dependency
refresh, September 11 resolver changes, Storybook startup, or production-build
performance. The archived measurements have not been regenerated for those
changes.

## Security Dependencies

The September 9 review recorded compatible updates removing the reviewed
`brace-expansion`, `fast-uri`, and nested `js-yaml` advisory ranges. Updating
the development-only npm bundle also cleared its affected bundled packages.
The September 9 refresh additionally updated locked `colord` from 2.9.3 to
compatible 2.10.0. The dated
[dependency assessment](../security-4.5.0.md) retains the exact Core and
fresh-consumer audit results and two residual `extract-zip` advisories in the
Pa11y browser-installation chain. That assessment supersedes the earlier
checkpoint's advisory counts. Its baseline is `6a74618` plus the recorded
`colord` lockfile patch; the archived Core and consumer hashes identify the
installations actually reviewed.

The later `fbbc6b9` refresh updates Storybook to 10.6.0, Vite's declared range
to `^8.3.0`, Emulsify CLI to 2.4.1, and other compatible dependencies. The
September 9 audit counts and managed-browser proof have not been regenerated
against that tree or the final release head. Keep their historical scope when
reviewing the [dependency assessment](../security-4.5.0.md).

Consumers must refresh their own lockfiles; Core's lockfile does not replace
a theme's locked transitives. Run the theme's `npm audit` and build checks
after refreshing. The security review records browser-installation exposure,
not a demonstrated site-visitor exploit. Its owner, acceptance, and review-date
decisions remain unresolved. An optional managed-browser configuration was
tested to avoid Puppeteer's download/extraction path; it leaves the dependency
findings visible and does not certify browser provisioning or patch maintenance.
Pa11y 10 is not forced into this release.

## Copied Audit Wrappers

Themes whose audit wrapper prints a documentation footer to stdout must add
`>&2` to that footer when using JSON output and preserve the audit command's
exit status. Use `npm run --silent audit -- --json` to omit npm's command echo,
or call `npx --no-install emulsify-audit --json` directly. The
[before/after migration example](../migration-4x.md#manual-packagejson-updates)
shows the small local edit. No theme regeneration is required.

The packed Drupal consumer checks the combined and Twig-only wrappers: the
entire stdout must be one JSON document, documentation footers go to stderr,
and success and failing-threshold exit statuses survive. Paths with spaces
and quotes exercise argument forwarding. Starter tests exercise their actual
generated manifests with an installed Core package and reject the old stdout
footer and a wrapper that masks failure.

## Compatibility Evidence And Repository Operations

The [versioned corpus](../twig-php-parity.md) records JavaScript and
pinned Emulsify Tools PHP output, including object BEM argument order,
utility-class punctuation, boolean overrides, ARIA list merging, escaping,
and context consumption. No helper output is harmonized. An optional manual
workflow checks both sides against pinned Tools and serializer revisions;
PHP/Composer are absent from ordinary npm development and the published
package. This verifies a pinned observation, not an officially supported
Core/Tools version pairing.

The recorded successful PHP workflow ran at `d02b8ea` on September 9; the
September 10 aggregate tested JavaScript parity at `bc0de261`. Neither is a
new PHP or final-dependency-tree parity run after `fbbc6b9`.

Workflow actions are pinned, Dependabot checks actions weekly, and superseded
PR validation can be cancelled. Integration pushes use distinct concurrency
groups. The existing publishing barrier and release rules are preserved.
Drupal-filter and performance documentation describe the existing opt-in and
fixture byte ceiling. The preview-head override and absence of
`imagemin-gifsicle` were verified in already published 4.4.0 when closing
issues #80 and #157; they are not new 4.5.0 runtime fixes.

`npm run release:verify` now writes ignored `.release-evidence/report.json`;
CI retains per-job `release-evidence-...` artifacts. The existing checks and
failure behavior remain in place. The
[report guide](../release.md#generated-evidence-for-the-checked-revision)
explains exact source/package identity, partial or unavailable results, and
the distinction between execution evidence and release approval. The
[September 8 checkpoint](4.5.0-verification.md) remains historical evidence.

## Migration Actions

1. Refresh the consuming theme's compatible dependency lockfile, then run
   `npm audit` and the project's checks.
2. Import the WCAG 2.2 preset only if the additional automated check is wanted.
3. Correct an old copied audit footer and preserve exit status, or invoke the
   audit executable directly.
4. Correct stale bare Twig paths that relied on discarding a missing first
   directory, and remove stale copied source files if output cleaning is disabled.

An existing supported 4.x consumer needs no regeneration or configuration
migration. Valid template references and helper output remain unchanged; the
incorrect fallback and copied-source cases above need attention. A consumer
upgrading from 4.2 on Node.js below 24.13.0 still encounters the historical
4.3.0 floor increase; 4.5.0 adds no further increase.

## Known Limits And Pending Decisions

Automated accessibility checks do not establish full conformance. Static
audits cannot prove arbitrary dynamic project behavior. The parity corpus
preserves known output differences. Consumer validation covers the documented
npm installation layout, not every package manager or linking model.

Residual browser-chain acceptance, ownership, and review dates remain
unresolved. Confidential security intake and the existing package-metadata/
license-file inconsistency also need a release-review disposition. Maintenance
windows, backports, supported Tools counterparts, and future helper
harmonization remain separate proposed follow-ups in the
[decision register](../maintainer-decisions.md); this release creates no such
commitments.

Publication remains the separate automated workflow after an authorized merge
to `main`. Passing verification does not grant human approval or accept risks.
